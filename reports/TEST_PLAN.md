# T6 Independent Test Plan & Acceptance Criteria (v1.0)

Owner: Testing & Technical Auditor (T6). Status: Phase 1 (plan) complete; Phase 2 (execution) starts as T2-T5 reach REVIEW.
Applies to: `/workspace/heading-monitor` (README.md rules, ARCHITECTURE.md interfaces, `contracts/*.schema.json`, TEAM_RULES.md).

**Evidence label for every numeric target in this plan: `[SIMULATED]`.** No target here is, or can become,
`[HARDWARE-VERIFIED]` until a raw RM3100/Matek log exists under `reports/hardware_logs/` and the auditor signs it off
(README rule 1). All tests are virtual (TEAM_RULES 10).

## 0. Method and independence
- Tests live in `tests/` (pytest), are black-box against the public interfaces in ARCHITECTURE.md, and are written
  only by T6. T6 writes no product code and does not edit other owners' files.
- **Independent truth model.** Heading/tilt test vectors are generated by T6's own reference model in
  `tests/refmodel.py` (rotation of an Earth-field vector by a known yaw/pitch/roll, NED body frame,
  x fwd / y right / z down, ZYX Euler), *not* by `sim/`. This prevents a shared bug in sim and core from cancelling out.
  Sim output is additionally checked end-to-end against its own `truth` block, and the sim's `truth` is cross-checked
  against the reference model.
- Default reference field `[SIMULATED]`: |B| = 50 uT, inclination 60 deg down, declination 0 unless stated
  (mid-latitude; India-like values, e.g. inclination ~ 20-40 deg, are also swept).
- Angular error is always the wrapped difference `((a - b + 180) mod 360) - 180`; RMSE/max computed on that.
- Repeatability: every stochastic test uses fixed seeds; runs repeated N=5 times, spread reported.
- Tests that cannot run because a deliverable is missing are recorded as **NOT RUN (missing)**, never as pass.

## 2. Position / navigation claims policy
A magnetometer + accelerometer heading is an *orientation* measurement. It cannot establish geographic position,
distance travelled, or speed, and it does not provide "GPS-independent navigation". Dead-reckoning claims would need
a velocity source and a demonstrated drift bound; nothing in this project scope supplies either. Any such claim is rejected
and filed as a defect against its owner (Q1).

## 3. Deliverable verdict rule
Each deliverable (T1-T5, plus PM docs) gets PASS only if all its criteria above pass (or are explicitly waived by the PM
in TEAM_TRACKER.md with reason) and its own test suite runs green under T6. Project completion is approved only when
`python -m app --source sim` runs end-to-end, Q4 passes, and all required reports exist
(`docs/hardware/FACTSHEET.md`, `docs/math/HEADING_MATH.md`, `docs/firmware/FC_SETUP.md`, sim README,
`reports/verification_report.md`).

## 4. Defect process
Defects are filed in TEAM_TRACKER.md as D1, D2, ... with owner, severity (CRITICAL / MAJOR / MINOR) and criterion ID.
CRITICAL = wrong heading convention/sign, crash on routine input, wrong source badge, fabricated or hardware-implied claim.

## LIMITATIONS (T6)
1. All targets are `[SIMULATED]`; they say nothing about the physical RM3100/Matek FC. No hardware log exists.
2. Simulation and reference model both assume an ideal dipole-free uniform Earth field; real environments (ferrous
   structures, wiring currents, temperature drift of offsets) are not represented beyond the sim's interference scenario.
3. MSP tests use hand-built frames from the public protocol description; actual firmware behaviour (rate limits, mag
   scaling per firmware version, whether MSP_RAW_IMU carries RM3100 data on our exact Matek board) is unverified.
4. The exact Matek FC model is unknown (T1 open question), so board-specific checks cannot be done.
5. UI checks are automated (HTTP/WebSocket + headless browser if available); human readability is not assessed.
6. Numeric targets are T6 proposals; the PM may tighten/relax them, recorded in TEAM_TRACKER.md.
